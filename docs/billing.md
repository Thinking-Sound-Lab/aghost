# Pricing and billing

Every plan includes MCP and REST API access, the dashboard, core comment-to-DM automation, inbox, click tracking, and unlimited automations, contacts and DMs within Instagram's limits and fair use. Growth adds product carousels; Business adds follow-up nudges. There is no free plan or trial in the billing catalog; free periods are given with discount codes (see [free periods](#free-periods)).

A workspace needs an active plan to use the product. Without one, a signed-in owner sees only the paywall, where they choose a plan, and the workspace's API keys are refused over REST and MCP. See [the paywall](#the-paywall).

| Plan     | Accounts | Monthly | Yearly | Added features                                              |
| -------- | -------- | ------- | ------ | ----------------------------------------------------------- |
| Pro      | 1        | $9      | $108   | Core automation tools                                       |
| Growth   | 2        | $19     | $228   | Everything in Pro, plus up to 10 product cards per carousel |
| Business | 5        | $49     | $588   | Everything in Growth, plus automatic follow-up nudges       |

All countries, including India, pay in US dollars. Prices include tax. Yearly billing costs twelve months, paid upfront. The plan definitions in `packages/api/src/contract/billing.ts` are shared with the UI; the backend validates Dodo's catalog against them before checkout.

## Carousel and follow-up rollout

1. Apply `20261016090000_carousels_and_follow_ups.sql`. It adds nullable carousel/reminder configuration and a workspace-scoped reminder queue; existing text automations are preserved.
2. Release the API before the dashboard. New request fields are optional: older clients preserve stored carousel/reminder settings when they omit them. Explicit `null` removes the feature. Feature access is checked by the shared domain services for dashboard, REST and MCP. Downgrades pause running automations that need a higher plan, and pending reminders recheck the plan before sending.
3. Add `message.sent` and `message.received` to the existing signed Zernio webhook at `<ApiUrl>/api/webhooks/zernio`. Keep `account.connected` and `account.disconnected`. `pnpm local:tunnel` configures all four for local use. No new keys, services or Dodo products are needed.
4. Release the dashboard and pricing page, then verify a carousel and nudge with a controlled Instagram account. Local tests use provider fixtures and are not proof of live Instagram delivery.

The API process polls durable reminder jobs every 15 seconds. Only successful main automation DMs create jobs; opening/follower postback gates are ignored. Select one reminder from 30 minutes to 20 hours, optionally with a link button. Before sending, the worker verifies the conversation and original DM, checks tracked clicks and later messages, and requires proof of a recent incoming message or resolved opt-in gate inside Instagram's 24-hour window. A comment alone never grants that permission. A reply cancels a pending reminder; clicks and newer conversation messages skip it at delivery time. Pausing, editing, deleting, disconnecting, or losing feature access prevents the old reminder from sending.

Claims survive process restarts and concurrent API replicas. Sends use a stable provider idempotency key derived from the original DM log; transport errors retry up to five times. Failed sends remain visible in automation activity. The worker does not reclaim the existing workspace mutex automatically; use the documented operator recovery for an API crash that leaves workspace ownership behind.

Waiting for a busy workspace reschedules the reminder without consuming a delivery attempt. Provider-history checks run outside workspace ownership with a bounded search; unverified original DMs are skipped. The worker reloads the plan and automation under ownership immediately before sending. A confirmed send receipt is retained on a failed status save so a subsequent worker records the original delivery time without sending or mistaking the nudge for a newer reply. Paused drafts can retain unchanged features after a downgrade; activating or adding unavailable features still requires the appropriate plan.

## Dodo setup

1. Set `DODO_PAYMENTS_ENVIRONMENT=test_mode` and `DODO_PAYMENTS_API_KEY` in the root `.env`.
2. Run `pnpm billing:setup`. It creates or updates six recurring SaaS products, tagged by plan and interval. Each product has a USD base price, tax-inclusive pricing, no trial, a card required even at $0, and no automatic country discounts. Reruns reuse the tagged products and archive all country and currency overrides. Duplicate product tags are refused. Disable Charm Pricing under Dodo's Settings → Business so checkout uses the exact advertised amounts. This is a business-wide setting that also affects other products in that business; the setup script does not change it.
3. Run `pnpm local:tunnel`. It registers a Dodo test-mode endpoint, stores its signing secret in `DODO_PAYMENTS_WEBHOOK_KEY`, and recreates the Docker API with it. The tunnel exposes only `/api/webhooks/zernio` and `/api/webhooks/dodo`.
4. Run `pnpm dev` and sign in. The paywall lists the plans; choose one to open hosted checkout. Use Dodo's [test payment methods](https://docs.dodopayments.com/features/payment-methods/india#testing).

For production, create the catalog in `live_mode` with that mode's API key. Explicit exported settings override the root `.env` in both billing commands. Register `https://<ApiUrl>/api/webhooks/dodo` in Dodo and subscribe to subscription events plus `payment.succeeded`, `payment.failed`, `payment.cancelled`, and `payment.processing`. Add all three Dodo values to the existing `aghost/prod/api` Secrets Manager JSON **before deploying the changed ECS task definition**. Use empty key/secret strings if billing is intentionally unavailable. Apply `20261011090000_workspace_billing.sql` and `20261011100000_billing_coordination.sql` before releasing the API.

Stop the previous API's writers during the initial billing rollout. With the migrated database, matching Zernio credentials and the correct Dodo mode configured, run `pnpm billing:reconcile` before reopening traffic to the new API. It collects every workspace with active automation rows and applies the webhook policy: paid workspaces within their account limit keep running; workspaces without a customer or subscription, ended plans and over-limit plans are paused at Zernio and in Postgres. A provider failure makes the command fail, and a rerun retries the remaining active rows. No workspace is implicitly grandfathered into a free plan.

Checkout requests USD and disables currency selection, so every country pays in USD even if Adaptive Currency is enabled in the Dodo account. Before creating a session, the backend checks Dodo's USD checkout quote against the advertised initial and recurring amounts and refuses checkout if account settings such as Charm Pricing change them. Pricing does not depend on hosting geolocation or country headers. Customers enter their billing address at checkout; Dodo uses it to calculate the tax included in the price. Confirm both India and non-India hosted checkouts in the configured Dodo account before releasing billing.

See [Adaptive Currency](https://docs.dodopayments.com/features/adaptive-currency), [tax-inclusive pricing](https://docs.dodopayments.com/features/tax-inclusive-pricing), and [India payment methods](https://docs.dodopayments.com/features/payment-methods/india). UPI and RuPay cards require INR billing and are unavailable with this USD-only catalog; Dodo rejects a RuPay card at a USD checkout with `INVALID_REQUEST`, even when a discount makes the total $0. Updating the catalog applies to new subscriptions; it does not change the price of existing subscriptions.

## Free periods

To give someone free time, create a discount code in Dodo with **Type** Percentage, **Amount** 100, **Subscription Cycle Limit** 1, and a **Usage Limit** of 1. Restrict it to the product with the interval you mean to give: one cycle of a yearly product is a free year, not a free month. The customer enters it at checkout and pays $0. Their card is still collected, and Dodo charges the full price at the next renewal. The products keep Dodo's **Card-optional at $0 Price** off (`zero_amount_payment_method_optional`): `pnpm billing:setup` turns it off, and checkout is refused while any product has it on. If that charge fails, the subscription goes on hold and the workspace is locked like any other.

Only a 100% percentage code unlocks a $0 checkout. A flat-amount code that brings the total to $0 leaves the workspace pending; give free time with a percentage code.

## The paywall

- The plan is checked on the server before every dashboard and agent request. Only billing (`/api/billing/*`) and the integration status (`/api/integrations`) answer without one, so that a workspace can subscribe; routes are behind the paywall unless they are marked `withoutPlan`. Everything else returns 402 `plan_required`, including a workspace's own accounts, automations, contacts, inbox and API key management.
- A plan grants access while its subscription is `active` or `past_due`. A new workspace, a checkout whose payment is still `pending`, and a subscription that is `on_hold`, `paused`, `cancelled`, `failed` or `expired` are all locked out.
- API keys follow their workspace. A valid key is answered with 402 on every REST path, the OpenAPI document and the MCP endpoint until the owner subscribes again; the key itself is not revoked and works again afterwards.
- The dashboard shows the paywall in place of every page and loads no workspace data until the plan is confirmed. If the plan ends while the dashboard is open, the next request is refused and the paywall replaces it.
- A locked workspace keeps its accounts, automations, contacts and history. They are not readable or changeable until it has a plan again. At the paywall any plan can be chosen, including one with fewer accounts than are connected, because accounts cannot be disconnected there; automations then stay off until the owner disconnects accounts or upgrades.
- Without Dodo credentials nobody can subscribe, so the app stops at the paywall. Configure Dodo's test mode to use the dashboard locally.

## Subscription lifecycle

- Only the authenticated workspace owner can start checkout, change plans, or open the billing portal. API keys and MCP do not expose billing mutations. Payer details come from the authenticated identity, and the backend fixes all return URLs.
- Each workspace has one durable checkout reservation. Retries resume its unpaid session for the same plan and interval, including one left at the payment form (`requires_payment_method`). Choosing a different plan or interval replaces an unpaid session with a new one, as does a failed or cancelled payment or expiry of Dodo's [24-hour, single-use checkout](https://docs.dodopayments.com/features/checkout). Dodo has no API to revoke a session, so a replaced link stays payable until it expires; a customer who pays two links holds two subscriptions, and the newer paid one becomes the workspace's plan. A session whose payment is processing is never replaced, even past link expiry. Checkout creation is reserved before the provider write and automatic SDK retries are disabled. A lost response or failed local save keeps the reservation for reconciliation, rather than issuing a second payable link.
- Checkout return and Manage billing return open Settings → Plan and Billing, or the paywall while the workspace has no plan. The UI reconciles with Dodo; it does not trust redirect query parameters. Customers can also refresh billing manually.
- Pricing cards preserve the plan and monthly/yearly selection through Google sign-in and initialize billing with that choice. These parameters select the UI only; they do not authorize payment or access.
- Webhooks verify the raw body with Standard Webhooks, including timestamp freshness. Subscription and payment events cause a read of Dodo's current subscription and payment records. Redeliveries and delayed events converge to the current state.
- Database ownership serializes checkout, subscription reads and saves, plan changes, account sync/removal, and automation writes per workspace across API instances. Billing and account webhooks locate the workspace first, then apply their changes under ownership. A plan shutdown waits for an in-flight activation, then pauses its result; an activation after shutdown fails its plan check.
- Existing subscription products are resolved independently by their metadata, including archived or repriced products. A missing or mismatched sales SKU still blocks new sales, but does not block cancellation or on-hold updates for another subscription.
- An initial active mandate does not grant access until Dodo reports a successful payment belonging to that subscription and customer that is either nonzero or made $0 by a 100% percentage discount code. A $0 payment without such a code is only a payment authorization. Indian payments can remain processing for about 48 hours. Existing paid subscriptions retain Dodo's `past_due` grace period and stop on `on_hold`, `paused`, cancellation, failure or expiry.
- Plan changes charge prorated amounts immediately and use `prevent_change` on payment failure. A returned payment approval URL is forwarded to the browser. Access reflects the provider's actual product after payment, not the requested product.
- The application blocks a downgrade while too many accounts are connected. A downgrade performed in Dodo's portal is still reconciled; automations are paused if it exceeds the new limit. They must be turned on again after the owner disconnects accounts or upgrades.
- Account callbacks hold the same workspace ownership as billing across provider reads, database saves and rejected-account cleanup. The database trigger also checks new connections against the current plan. A downgrade sees completed callbacks before counting accounts; an upgrade and reconnection wait for old provider cleanup. A connection exceeding the plan is stored as disconnected and removed from Zernio. A failed provider disconnect is retried when the webhook is redelivered, even if the database event was already committed; the rejection is rechecked under ownership so a duplicate cannot remove an account that has since been allowed.
- When the plan ends, the backend fetches every automation page, including older rows beyond Supabase's 1,000-row response limit, and pauses running automations at Zernio before marking them paused locally. Failed pauses fail the webhook request so Dodo can retry. The subscription is kept for payment recovery, and the workspace is locked behind the paywall. After the owner pays again, the automations are still paused and must be turned on again.

## Recovery after interrupted provider operations

Workspace ownership deliberately does not expire automatically: an older process might still be writing to Zernio or Dodo. Normal success and errors release ownership. A crashed process or a failed release leaves a row in `workspace_operations`; later mutations return a retryable conflict instead of overlapping it. After stopping the old process and checking its provider writes, use a service-role connection to release only the observed claim with `release_workspace_operation(workspace_id, owner)`, then rerun billing reconciliation. Do not release a claim solely because it is old.

If `workspace_billing.checkout_plan` is set but `checkout_session_id` is null, a checkout creation response or save was lost. Check that customer's Dodo sessions and subscriptions before retrying. Restore the original session id and URL when available, or clear the checkout columns only after confirming that any issued link has expired and no payment or subscription is unsettled. A reservation that has a session needs no operator action to change the selected plan; the next checkout replaces it. Failed pricing validation happens before reservation, so correcting the sales catalog or Charm Pricing configuration needs no checkout recovery.

## Verification

`pnpm setup:test` starts this project's local Supabase and applies pending migrations without resetting data. `pnpm verify` runs typecheck, lint, tests, and the production build. Billing tests use the installed Dodo SDK with an in-process fixture transport, plus real local Postgres/Auth for the HTTP lifecycle, the paywall for sessions and API keys, tenancy, checkout deduplication, stale subscription reads, activation/shutdown ordering, legacy reconciliation and concurrent account limits. They never call a live payment provider. A configured hosted checkout and actual sandbox payment must still be verified with Dodo credentials.
